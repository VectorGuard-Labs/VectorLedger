Cryptographic Primitives & Hash Chain

VectorLedger's tamper-evidence is built on BLAKE3 hash chains, AES-256-GCM encryption, Ed25519 signing, and binary Merkle trees. This view explains the actual algorithms used in the codebase.

BLAKE3 Hash Chain

Every journal entry contains three hashes that form an unbroken chain from first entry to last. Modifying any past record invalidates every subsequent chain hash.

content_hash = BLAKE3(canonical_bytes_of_entry)
chain_hash = BLAKE3(sequence.to_le_bytes() ‖ prev_chain_hash ‖ content_hash)
First entry: prev_chain_hash = 0000…0000 (ZERO_HASH, 64 hex zeros)

Why BLAKE3? ~3× faster than SHA-256 on modern CPUs via SIMD/parallelism. 256-bit output. Designed for content-addressed storage. Domain separation (0x00 for leaves, 0x01 for nodes) prevents second-preimage attacks.

Binary Merkle Tree

A single Merkle root commits to the entire database state. Clients can verify that a specific entry is in the committed state using a compact proof without downloading the whole database.

Leaf: hash_leaf(data) = BLAKE3(0x00 ‖ data)
Internal node: hash_node(left, right) = BLAKE3(0x01 ‖ left ‖ right)
Odd layer: last leaf is duplicated
Empty tree: returns ZERO_HASH

MerkleProof structure (from merkle.rs)

pub struct MerkleProof {
    pub leaf_index: usize,
    pub leaf_hash: Hash,       // [u8; 32]
    pub path: Vec<ProofStep>,  // sibling at each level
    pub root: Hash,
}

pub struct ProofStep {
    pub sibling: Hash,
    pub sibling_is_left: bool,
}

// Verify: walk path, compute hashes, compare to root
impl MerkleProof {
    pub fn verify(&self) -> Result<(), CryptoError> {
        let mut current = self.leaf_hash;
        for step in &self.path {
            current = if step.sibling_is_left {
                hash_node(&step.sibling, &current)
            } else {
                hash_node(&current, &step.sibling)
            };
        }
        if current == self.root { Ok(()) }
        else { Err(CryptoError::MerkleProofInvalid) }
    }
}

WORM Audit Log

The audit log is a separate, independently chained WORM (Write-Once Read-Many) log at audit/audit.log. Every write is fsync'd. The log has its own BLAKE3 hash chain independent of the ledger chain.

content_hash = BLAKE3(seq_le8 ‖ ts_nanos_le8 ‖ event_kind_json_bytes)
chain_hash = BLAKE3(seq_le8 ‖ prev_chain_hash_hex_bytes ‖ content_hash_hex_bytes)
Note: audit chain hashes are computed over the hex-encoded bytes (ASCII), unlike the ledger which uses raw bytes.

Four-Eyes Dual-Control Approval

When an account has require_four_eyes = true, entries must be approved by a second, different principal before posting to the ledger. The queue is stored in JSONL files at vledger-data/foureyes/ (all 0o600 permissions).

Lifecycle

StatusDescription
PendingWaiting for second approver. Stored in pending.jsonl
ApprovedEntry posted to ledger. Moved to approved.jsonl
RejectedEntry NOT posted. Moved to rejected.jsonl

Key Constraints

  • Self-approval prevented: FourEyesError::SelfApproval if approver_id == submitter_id
  • Idempotency guard: approve() checks approved.jsonl first; if found, returns existing record without re-posting (crash-safe)
  • Atomic rename: pending.jsonl.tmp → pending.jsonl (Unix atomic)
  • All state changes fsync'd before returning
  • Audit events written for all three actions

Compliance Evidence Report

VectorLedger generates machine-generated technical evidence supporting SOC 2 Type II and PCI-DSS v4 control assessments. Evidence is computed by inspecting the actual data directory structure — not pre-written documentation. The control statuses on this page (PASS / WARN / FAIL) are illustrative samples, not results from your data directory. Run vledger compliance-report for real results.

SOC 2 Type II — 8 Controls

A report is COMPLIANT if zero FAIL results (warnings allowed). Generated via vledger compliance-report --standard soc2. Typical date range: last 90 days.

CC6.1
Logical access — TLS encryption in transit
TLS 1.3 is mandatory for all connections (rustls). Checked: catalog/VERSION file exists (proxy for initialized database).
CC6.2
Audit trail records all authentication events
Checked: audit/audit.log exists. Reports file size. Every auth_event (success or failure) is written to the WORM log.
CC6.3
Access revocation — account close mechanism
close_account() persists AccountStatus::Closed via WAL. Closed accounts reject all new entries at LedgerStore. Checked: wal/ directory exists.
CC6.6
Encryption at rest
All page-store files encrypted with AES-256-GCM. Per-table keys derived from master key via HKDF. Checked: pages/ directory exists.
CC6.7
Transmission encryption — TLS configuration
WARN if self-signed cert (catalog/tls_cert.pem). PASS only if CA-signed cert at keys/server.crt. Self-signed certs do not satisfy SOC 2 CC6.7 in production.
CC7.2
Audit log chain integrity monitoring
Calls AuditLog::verify_chain() — reports event count. FAIL if chain broken. The audit log's own BLAKE3 hash chain is independent of the ledger chain.
CC8.1
WAL append-only change record
WAL provides append-only change record for all ledger mutations. Checked: wal/ directory exists, segment count reported.
A1.1
High-availability replication
WARN (not FAIL) if replication.json absent — single-node deployment with documented backup strategy is an accepted alternative. PASS if replication.json present.

Generated via vledger compliance-report --standard pci-dss. Typical date range: last year.

PCI-2.2
Secure system config — master key storage
FAIL if keys/MASTER_KEY_PLACEHOLDER.txt exists (key is on disk, not in HSM). PASS if that file is absent. Action: move master key to HSM and delete the placeholder.

PCI-7.1

PCI-10.2
Audit trails for all access to cardholder data
Checked: audit/audit.log exists. All QueryExecuted, EntryPosted, AuthEvent events recorded. File size reported.
